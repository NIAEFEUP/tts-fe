# tts-be

Backend for TTS, built with [Bun](https://bun.sh), [Elysia](https://elysiajs.com), and [Prisma 8](https://www.prisma.io/docs/orm/v8).

## Prerequisites

- [Bun](https://bun.sh) >= 1.4
- A PostgreSQL >= 15 database

## Setup

```bash
bun install
echo 'DATABASE_URL=postgres://...' > .env   # git-ignored; see .env.schema for every variable
```

---

## Running locally

```bash
bun run dev
```

Starts the Elysia server at `http://localhost:3000` with hot reload.
Environment variables are declared in [`.env.schema`](./.env.schema) and validated by [varlock](https://varlock.dev) before the server starts (`bun run dev` and `bun run start` fail with a readable error if, for example, `DATABASE_URL` is missing). Values come from the process environment or a git-ignored `.env` / `.env.local`. Run `bunx varlock load` to check your configuration without starting the server.

The `db:*`, `migrate*` and `migration:status` scripts run through varlock too, so they pick up the same values.

## Database

The DB schema and runtime client live in `src/infrastructure/database/`:

| File              | Purpose                                                     |
| ----------------- | ----------------------------------------------------------- |
| `contract.prisma` | Your schema — the source of truth. Edit this.               |
| `contract.json`   | Generated by `contract:emit`. Do not edit.                  |
| `contract.d.ts`   | Generated by `contract:emit`. Do not edit.                  |
| `prisma.ts`       | Runtime client. Import `db` from here in your repositories. |

## Seeding

Two scripts seed the local database. Both **truncate every table first**, so
they are safe to re-run and always produce the same deterministic ids
(`CourseUnit` / `Class` starting at 1).

| Script              | Populates                                                                                                                        |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `bun run db:seed`   | **Catalog only** — faculty, courses, course units and occurrences, from the committed fixture.                                    |
| `bun run db:seed:demo` | **Catalog plus the mock exchange layer** — users, classes, enrollments, exchange windows, sample exchanges and enrollment requests. |

> ⚠️ **The two are mutually exclusive.** Both run the same reset, so `db:seed`
> wipes the demo data (leaving `ExchangeItem`, `ExchangeRequest`, `User`, etc.
> empty) and `db:seed:demo` re-creates it. If you want exchanges, always finish
> with `bun run db:seed:demo` — running `bun run db:seed` afterwards empties them.

- The **catalog** is real scraper data, extracted into
  [`src/scripts/fixtures/feup-leic-meic-mesw.json`](./src/scripts/fixtures/feup-leic-meic-mesw.json)
  by `bun run catalog:extract` (which reads the repo-root `database.db`).
- The **mock layer** is hand-authored and covers **L.EIC and M.EIC only** — MESW
  is in the catalog but is not part of the exchange feature.
- The demo admin is **you**: set `ADMIN_UP` to your NMEC ("up" number) in `.env`
  and `db:seed:demo` seeds that account. Its role is set by `ADMIN_ROLE`
  (`USER` | `ADMIN` | `SUPERUSER`, default `ADMIN`). Both are declared in
  [`.env.schema`](./.env.schema).
- Both seeds refuse to run unless `DATABASE_URL` points at a loopback host.

## Starting from scratch (first time)

### 1. Write your schema

Open [`src/infrastructure/database/contract.prisma`](./src/infrastructure/database/contract.prisma) and define your models:

```prisma
// use prisma-8

model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String?
  createdAt TimestamptzString @default(now())
}
```

### 2. Emit the contract artefacts

```bash
bun run contract:emit
```

This generates `contract.json` and `contract.d.ts` next to `contract.prisma`.
**Run this every time you change `contract.prisma`.**

### 3. Apply the schema to the DB (first time only)

```bash
bun run db:init
```

Creates all tables, indexes, and constraints, and writes Prisma's internal marker
row so it can track future migrations.

### 4. Use the client in your code

```ts
import { db } from '@/infrastructure/database/prisma'

const users = await db.orm.public.User.select('id', 'email').all()
```

## Changing the schema

Every schema change follows this loop:

```
edit contract.prisma → emit → (dev: db:update) or (shared/prod: plan → migrate)
```

### Quick path — local dev only

Use this while iterating fast on your own machine. It applies the diff directly
without writing a migration file.

```bash
# 1. Edit contract.prisma
# 2. Regenerate artefacts
bun run contract:emit

# 3. Apply directly to your local DB (no migration history written)
bun run db:update
```

> ⚠️ Never use `db:update` against a shared or production database.
> It leaves no migration history and cannot be replayed.

### Formal path — shared environments and production

Use this for any change that needs to be reviewed, version-controlled, and
replayed across environments (staging, production, teammates' DBs).

```bash
# 1. Edit contract.prisma
# 2. Regenerate artefacts
bun run contract:emit

# 3. Plan the migration — Prisma diffs contract vs. last known DB state
#    and writes a new directory under migrations/app/<timestamp>_<name>/
bun run migration:plan -- --name <slug>
# e.g.: bun run migration:plan -- --name add_users_table

# 4. Review the generated files (see below)

# 5. Apply the migration
bun run migrate
```

#### What gets generated

Each `migration:plan` writes a directory like:

```
migrations/app/
└── 20261001T1200_add_users_table/
    ├── migration.json   ← manifest (hash, from/to contract hashes)
    ├── ops.json         ← canonical operation list (do not edit directly)
    └── migration.ts     ← TypeScript source you can review (and edit for data transforms)
```

#### Inspect a migration before applying

```bash
# Show a single migration package
bun run migration:show -- <dir-name-or-hash-prefix>
# e.g.: bun run migration:show -- 20261001T1200_add_users_table

# Preview the full ordered execution plan (reads DB, no writes)
bun run migrate:show
```

## Data transforms (backfills)

When you add a `NOT NULL` column with no default, Prisma can't know how to
backfill existing rows — it leaves a `placeholder(...)` in `migration.ts` for
you to fill in.

**Signs you need a data transform:**

- `bun run migration:plan` output shows `pendingPlaceholders: true`
- `bun run migrate` throws `MIGRATION.UNFILLED_PLACEHOLDER`

**How to fill it:**

1. Open the generated `migration.ts`
2. Replace the `() => placeholder("slot-name")` arrows with real query closures
   built against `endContract` (the end-state client)
3. Re-emit the migration package (self-emit):
   ```bash
   node migrations/app/<dir>/migration.ts
   ```
4. Apply:
   ```bash
   bun run migrate
   ```

---

## Migration mental model

Prisma 8's migration graph is a set of **edges** between contract hashes.
There is no implicit "tip" or "head" — the planner needs to know where to start.

**The `db` ref** (`migrations/app/refs/db.json`) is a pointer to the contract
hash your local database was last brought to. `db:update` and `db:init` write
it automatically. `migration:plan` reads it as the default origin.

**The flow:**

```
db:init / db:update  →  writes db ref
migration:plan       →  reads db ref as origin, writes new migration dir
migrate              →  applies pending migrations, advances the DB marker
```

**Important:** after a plain `bun run migrate` the `db` ref lags behind.
Refresh it with `bun run db:update` (no-op on the DB if already current),
or use `--advance-ref db` during migrate.

## Diagnostics

### Check migration status

```bash
bun run migration:status
```

### Verify the DB matches the contract

```bash
bun run db:verify
```

Exits `0` = clean. Exits `4` = drift found (marker mismatch, schema mismatch).
Use after manual SQL edits, restores, or failed migrations.

### Inspect the live DB schema

```bash
bun run db:schema
```

### Re-sign the marker (after a manual DB fix)

If you manually fixed the DB and it matches the contract but the marker is
stale, re-sign it:

```bash
bun run db:sign
```

## Recovering from common errors

| Error                            | Cause                                           | Fix                                                               |
| -------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| `MIGRATION.HASH_MISMATCH`        | `migration.ts` was edited without self-emitting | `node migrations/app/<dir>/migration.ts`, then `bun run migrate`  |
| `MIGRATION.UNFILLED_PLACEHOLDER` | Placeholder not filled in `migration.ts`        | Fill the transform, self-emit, then `bun run migrate`             |
| `MIGRATION.PLAN_ORIGIN_UNKNOWN`  | No `db` ref and migrations already exist        | Run `bun run db:update` to reset the ref, or pass `--from <hash>` |
| `MIGRATION.HASH_NOT_IN_GRAPH`    | `db` ref points past the graph                  | `bun run migration:ref:set -- db <hash>`, then re-plan            |
| `CONTRACT.MARKER_MISSING`        | DB has no marker (fresh DB or wipe)             | `bun run db:init`                                                 |
| `CONTRACT.MARKER_MISMATCH`       | DB is at a different contract version           | Run a migration forward, or `bun run db:sign` if DB is correct    |

## Linting and formatting

The monorepo uses [Oxlint](https://oxc.rs/docs/guide/usage/linter.html) for linting and [Oxfmt](https://oxc.rs/docs/guide/usage/formatter.html) for formatting. A Husky pre-commit hook runs both automatically on every commit.

If you want to be safe before committing, run:

```bash
bun run lint        # check for lint errors
bun run format      # auto-format everything
```

Then commit. The pre-commit hook will run the same checks and should pass.
